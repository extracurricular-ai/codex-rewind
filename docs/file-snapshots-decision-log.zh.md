# Codex File Snapshots / Rewind —— 产品决策与讨论汇总

> 本文档汇总了该功能从最初调研到 Phase 2 落地全过程中的关键产品决策、设计澄清与讨论时间线。
> 正式设计规格见 `docs/rfc-file-snapshot-rewind.md`(英文,面向 upstream)。

---

## 一、项目缘起

从一个调研问题开始:**Claude Code、opencode、Codex 三个 CLI 是否有 rewind 功能,原理是什么?**

调研结论(全部经代码级核实):

| | Claude Code | opencode | Codex |
|---|---|---|---|
| 形态 | `/rewind`(双击 Esc),恢复代码/对话/两者可选 | `/undo` `/redo` `/timeline`,对话+文件一起回退 | backtrack(双击 Esc)**仅对话**,fork 式 |
| 文件快照 | 逐文件副本(`~/.claude/file-history/`),无 git | shadow git 仓库(write-tree),需项目是 git 仓库 | **无**——ghost-commit 功能曾存在,因数据丢失事故(#8214)被 un-ship 后彻底删除 |
| 覆盖范围 | 只追踪自家工具编辑过的文件 | 整个工作区 | — |

由此产生本项目的目标:**给 Codex 补上文件层 rewind,综合两家之长,规避 ghost-commit 的三条死因**(死因:①在用户真实 git 仓库里操作;②用临时 index 丧失 stat cache 导致快照极慢;③残缺快照迫使复杂的 untracked 记账)。

## 二、核心产品决策(按决策人视角逐条)

### 架构方向
1. **综合方案**:workspace 内 = opencode 式全景快照(类 git 扫描),workspace 外 = Claude Code 式 track-on-edit 动态追踪。
2. **完全不依赖 git**:不需要 git 完整功能,自建"内容寻址 blob + manifest + hash/mtime stat cache"(= 复刻 git 有用的 10%),速度问题由 stat cache 解决。
3. **bash/外部改动的覆盖策略**:不做逐命令拦截——workspace 内靠"多加 checkpoint"(每条消息前 + 内部改动前)自然兜住。

### 追踪范围
4. **独立 ignore 文件**,与 `.gitignore` 分离:git 不追踪的文件(如临时文档)会话历史可以追踪,反之亦然。
5. **workspace 根解析双模式**:向上查找最近的父 codex 项目 marker(与 git 相同的解析逻辑);找不到则进入 fallback 模式,追踪调用目录内容。
    - **[已推翻 · 2026-08-10]** 改为跟随会话自己的 `workspace_roots`,marker 向上查找降级为**兜底**(仅当没有配置任何 root 时使用)。
    - 推翻理由:向上找 `.git` 回答的是"**版本控制从哪开始**",而不是"**用户在做什么**",两者在两个方向上都会背离——monorepo 把标记放在实际工作位置之上很远(正是 #29388 的过度捕获形态),而非仓库目录退回调用目录,又可能落在实际编辑位置**之下**(实测:cwd 是空的 `inner/`,agent 在父目录工作,扫描一无所获)。codex 本来就有头等答案:`workspace_roots` 是多根、用户配置的,而且**沙箱正是按它决定 agent 能写哪里**——范围与它重合,"能改的都能回退"才是结构性保证而非巧合。
    - 连带后果:范围变成复数,manifest 记录它实际走过的根(`scope_roots`);"完整"只对声明覆盖的根内有效,否则会把 track-on-edit 从磁盘各处捡来的路径的缺席误判成删除证据。
    - **不要改回**:"父目录有 git 就该用 git 根"这个直觉很自然,但它恰恰是被否决的那条。范围应与**会话**一致,不与最近的 git 一致。
    - **[连带后果作废 · 2026-08-11]** `scope_roots` 与 `complete` 随决策 26 一并删除,manifest 不再记录它走过哪些根。**主决策不变**:根仍然来自 `workspace_roots`,仍然是复数,仍然只在没有配置时才回落到 cwd。变的只是"记录范围以便判断完整性"这件事本身没有必要了——删除依据改成墓碑之后,**没有任何判断需要知道扫描覆盖了哪里**(决策 26)。
    - 特别注意:git 在决策 26 里重新出现,但**只作为文件清单的来源之一**,不作为范围的边界。`git_tracked_files(root)` 读的是 `root` 这个根上的索引,根还是会话给的那个。上面"不要改回"的那条**仍然完全有效**。
    - **[澄清 · 2026-08-11 · 这条注释本身导致了一个 bug]** 上面那句"读的是 `root` 这个根上的索引"是**错的**,而且正是它让实现选了 `gix::open`(只在 root 自己就是仓库时才成功)。后果:**任何在仓库子目录里开的会话,git 分区完全是空的**——实测 `codex-rs/tui` 拿到 0 个文件,而索引里有 1,419 个。
    - 根因是**两种 walk-up 从来没有被区分开**,而本条的"不要改回"通篇讲的是前者,读者没有任何线索知道还有后者:
      - **范围的 walk-up(被否决)**:让 `.git` 所在的那个目录**变成范围根**。这就是本条否决的东西,**依然否决**。
      - **发现的 walk-up(必需)**:往上找 `.git/index` **这个文件在哪**,而范围根**原地不动**,仍然是会话给的那个。找到索引之后把条目**裁剪**回 root 以内。
    - 两者不是同一个操作:后者不会移动范围,一毫米都不会。判据写成可检验的形式:**对任意 root R,`git_tracked_files(R)` 返回的恰好是索引里位于 R 之下的那些条目,无论 R 是不是仓库根**——同一个子目录,不管会话是在 R 开的还是在它上面的仓库根开的,结果必须一样。
    - **教训**(这条比 bug 本身重要):文档写清楚了**意图**("git 只是文件名来源"),却把**机制**写成了一个具体而错误的实现描述。读者会照着机制写,不会照着意图写。
6. **fallback 护栏拒绝排除表和文件大小限制**(太不灵活),采用活跃度模型:≤50 个文件全部纳入;>50 则按 mtime 取最近更新的 30 个作种子;追踪硬上限 100,由 track-on-edit 增长。
    - **[已推翻 · 2026-08-11]** 改为**三分区**(决策 26)。50/30/100 这套数字连同 `SeedPolicy`/`TrackedSet` 一起删除。
    - 推翻理由:这条护栏只装在 **fallback 模式**上,而 fallback 是最不常见的那条路;有 git 的目录走的是全量子树扫描,**没有任何上限**——实测 codex 仓库 58,116 个文件 / 100,812 MB / 920 ms,其中绝大多数是构建产物。护栏装错了地方。
    - **部分保留**:排除表在决策 26 里以另一种身份回来了(`RECENT_SKIP_DIRS`),但回答的是另一个问题——见决策 26 的说明,那不是对本条的反悔。文件大小限制同理。

26. **追踪范围改为三分区并集,彻底放弃"扫子树"**(你提出)。
    - **触发**:先是发现 fallback 与 git 目录行为不一致(护栏只装在 fallback 上),量化之后问题的规模才清楚——codex 仓库一次全量扫描 **58,116 个文件 / 100,812 MB / 920 ms**。你的判断是"我现在开始觉得 `complete` 是个错误决定了,应该是永远有上限",并直接给出了替代结构。
    - **三个分区,各自回答不同的问题,各自的上界都不是目录树的大小**:
      1. **git 已追踪区** —— 读 `.git/index`。**不设上限,全量追踪**(你的决定)。上界是"项目自己认为属于自己的东西",而不是"往里面构建过多少东西":同一棵 100 GB 的树在这里只有 **5,996 个文件 / 56 MB / 236 ms**,因为构建产物恰恰就是没被提交的那部分。没有仓库时这一区为空,不是错误。
      2. **edit 累加区** —— agent 自己写过的路径,整个会话累加,**无上限**(Claude Code 同款)。它的大小由 agent 干了多少活决定,不由磁盘上有什么决定,而且每一条都是有人**特意**改过的文件。
      3. **最近修改区** —— 兜底。上限 **100** 个文件、单文件 **16 MB**、跳过常见构建/缓存目录。实测 **100 个 / 2.4 MB / 160 ms**。
    - **合计 ~6,096 个文件 / ~59 MB / 425 ms**,相对全量扫描是文件数 **1/11.6**、字节数 **1/1,975**、耗时 **1/3.4**。
    - **两次测量之间的漂移比任何一次单独的数字更有说服力**:同一个 checkout 隔了几小时再测,全量扫描从 58,116 文件 / 100,812 MB 涨到 **70,609 文件 / 116,134 MB**(多 21% 的文件、多 15 GB),纯粹是因为中间编译过。而 git 区**一动没动**(两次都是 5,996)。一个随着"这个仓库被用了多久"增长的成本,是没法预算的成本。
    - 复现方式留在了 `codex-rs/file-snapshots/examples/scan_bench.rs`——RFC 里引用的数字必须能在别人的仓库上验证,否则就只是我们这一棵树的轶事。
    - **`RECENT_SKIP_DIRS` 不是决策 6 的回潮**:决策 6 否掉排除表,是在回答"**留下什么**",结论是用活跃度而不是白名单——那条**依然成立**。这里的排除表回答的是另一个问题:`target/`、`node_modules/` 这类目录**每时每刻都在变**,按"最近修改"排序它们永远排在最前面,100 个名额在碰到第一个源文件之前就用光了。排除它们是**让活跃度信号可用的前提**,不是活跃度的替代品。
    - **为什么并集而不是优先级**:三个分区会重叠(git 追踪的文件也可能刚被 edit 过),取并集意味着不需要任何仲裁规则。再并上 `already_known`(这条线程以前观察过的全部路径,含墓碑),保证**会话内只增不减**——一个文件被 `git rm` 之后不会突然从追踪里蒸发,否则本轮就没人记得它曾经存在,回退时也就无从恢复。
    - **[修正 · 2026-08-11 · 上面这句话字面上就是那个 bug]** "再并上 `already_known`"描述的是一个**先各自算完、最后合并**的顺序,实现照做了,于是第三分区的 100 个名额是在**全部文件**里选完、再靠 `BTreeSet` 去重的——**名额在去重之前就花掉了**。
    - 实测浪费:仓库根 **97/100** 是重复项;子目录会话 **100/100**,这个分区的贡献是**零**。
    - 正确顺序:①② 先算,**把结果作为"已覆盖集合"传给 ③**,③ 在**排序取前 100 之前**过滤。上限是一份**预算**,预算花在重复项上等于没花。
    - 什么时候会真的丢覆盖(而不只是浪费):只要有 ≥100 个 git 已追踪的文件比某个未追踪文件更新,那个文件就被挤出榜单。`cargo fmt`、切分支、跑一次代码生成,随便哪个都会一次性刷新几百个文件的 mtime。
    - **教训**:凡是"上限/预算"类的参数,文档必须同时写清楚**在什么集合上取**,否则"取最近 100 个"这句话是有歧义的,而两种读法的行为差一个数量级。
    - **唯一漏掉的**:离开 git 追踪、且此后只被 shell 改过、且掉出最近 100 名的文件。你自己指出第三分区能兜住其中的绝大部分,确实如此——要同时满足三个条件才会漏。

27. **读 `.git/index` 用 gix,不 shell out 调 `git ls-files`**(你选的)。索引是一个**文件**,`git ls-files` 是一个**进程**,而这段代码在每一轮对话开头都要跑。gix 已经在 codex 的依赖树里(`git-tooling` 在用),不引入新依赖。副作用:不依赖用户 PATH 上有没有 git、是哪个版本。

28. **上限参数:git 区不设、最近修改区 100 个、单文件 16 MB**(你定的)。
    - **git 区不设上限**——"项目提交了什么,那就是项目的内容,多大都是",所以 16 MB 的限制**只作用于第三分区**。
    - **100 这个数字**:你的原话是"应该也能覆盖 95 以上场景了吧,我们需要找一个平衡,不是越大越好"。它只需要兜住"git 之外、又不是 agent 自己改的"这个残差,不需要覆盖整个工作区。
    - **16 MB 的来历是一次被你纠正的推导**。我最初按当前仓库的 p95 提了一个小得多的阈值,你指出"**你的 p95 只适用于当前仓库而不是整个代码世界,我建议增大**"——这是对的:生成代码、lock 文件、notebook、测试 fixture 动辄几 MB,都正是用户想要回来的东西。这个阈值的职责是挡掉**病态对象**(媒体、模型权重、数据库文件),不是给文本划线,所以要定在远高于文本的地方。

4b. **独立 ignore 文件在三分区之后仍然保留**(你专门确认)。理由:它是**唯一**能从三个分区里排除追踪、并且能与 `.gitignore` 排除**不同**文件集合的黑名单机制。三分区都会经过 `is_ignored`,语义仍是对称的(不快照、不恢复、不删除)。
    - **与 `.gitignore` 的关系,以及"用户改了 `.gitignore` 怎么办"**:我们**不读** `.gitignore`,只读 `.codexsnapignore`(同样的语法)。但第一分区读的是 git 索引,而索引本来就已经排除了 git 忽略的文件——所以 `.gitignore` **间接**影响第一分区(改了它、并且 `git add`/`git rm --cached` 之后才生效),`.codexsnapignore` **直接**影响全部三个分区。
    - **不拦截用户编辑 `.gitignore`,只写清楚**(你的决定)。理由与决策 8 一致:以当前版本为准,与 git 自身的语义保持一致比自作聪明更可预测。

6b. **隐藏文件默认不追踪**:初始工作目录扫描跳过所有点开头的文件和目录(`.env`、`.vscode/`、`.venv/`、`.cache/` 等),`.git` 无论如何都排除——它们绝大多数是工具状态而非工作产物,跟着一轮对话被回滚是意外甚至破坏性的(`.env` 里可能是密钥)。**例外**:被 edit tool 显式改过的隐藏文件仍然追踪、仍可恢复(如 agent 修改的 `.github/workflows/ci.yml`),因为那是工作产物。需要全扫的人用 `[file_snapshots] track_hidden_files = true`,但 `.git` 即使开了也不扫。

### 正确性语义
7. **对称 ignore**:被 ignore 的路径不快照、不恢复、**删除时也不碰**——一条规则取代 ghost-commit 的整套 preexisting-untracked 记账。
8. **ignore 规则以当前版本为准**:恢复时读**当前** ignore 文件;若回退把 ignore 文件也换了,此后按新版生效——与 `.gitignore` 被 git 版本化的语义一致("gitignore 验证过的逻辑")。*(后续修订:`.codexsnapignore` 自身也是隐藏文件,按决策 6b 同样只在被 agent 编辑后才进快照——ignore 文件不再享有特殊待遇,规则因此更统一。)*
9. **加入 opencode 的 redo**:恢复前先拍安全 checkpoint,任何恢复可逆;在 codex 的 fork 模型下 redo 反而更简单(原线程天然保留)。
    - **修订(实现中发现):redo 记录是栈,不是"最后一次"**。回退压栈、撤销弹栈。若撤销只是"恢复最后一条记录",连续两次回退后的第二次撤销会把**第一次撤销**反过来——文件在两个状态间来回跳,而对话却在持续往回走。每一步单看都对,合起来是最难查的那种不一致。弹栈后 N 次撤销正好回溯 N 次回退,与对话侧沿 fork 父链回溯同步。
10. **删除规则**(实现中两次精化):只在有确凿证据时删除——目标 manifest 是全量扫描(缺席即不存在);从未见过的文件永不删除。*(二次修订:原先还有"目击出生"这条旁路,后来连同整个历史回溯一起删掉了——见决策 20,恢复计划只比较两个 manifest,不再走历史。)*
    - **[三次修订 · 2026-08-11]** 加回第二条独立依据:**墓碑**。edit 钩子发现文件是本轮**新建**(没有 pre-image 可存)时,不再什么都不记,而是显式记下"此路径当时不存在"。
    - 理由:原先"缺席"只是**隐含**的——它成立的前提是"我扫了全部",也就是 `complete` 所断言的、而有界捕获给不出的东西。于是 fallback 模式和范围外新建的文件**永远删不掉**:改动能撤,新建撤不掉,回退只完成一半。墓碑是一次**观察记录**而非全称推断,所以能独立成立,不依赖扫描完整性。
    - Claude Code 用另一条路走到同一结论:它的逐文件备份对不存在的文件写 `backupFileName: null`,回退读到 null 就删文件。
    - **[四次修订 · 2026-08-11]** 删掉第一条依据,**只留墓碑**。`complete` 标志、`scope_covers()`、`Manifest.scope_roots` 全部删除。
    - 理由:一旦承认追踪永远有上限(决策 26),`complete` 就**永远为假**,它断言的"我扫了全部"没有任何一条路径还能成立。留着一个恒假的字段,唯一的作用是让每次读代码的人再推导一遍它为什么恒假。
    - 关键在于:这**不降低能力**。`complete` 曾经独有的战果是"删除 shell 新建的、位于扫描范围内的文件",而三分区的第三分区(最近修改)本来就会把这种文件捡进下一次 checkpoint——捡进来就有墓碑,有墓碑就能删。真正丢掉的只有一种文件:**离开 git 追踪、且此后只被 shell 碰过、且不在最近 100 个之内**。这个交集窄到可以接受,而换来的是删除规则从两条降到一条,且那一条不依赖任何全称断言。
    - 连带简化:`capture()` 不再收 scope 参数,`plan_restore()` 的删除分支从两个塌成一个,`vanished_files_are_skipped` 这个测试改名叫"a path that is not there is recorded as not there"——旧名字描述的正是被推翻的行为(把证据当噪音丢掉)。
11. **GC 用引用计数**,快照生命周期 = 会话生命周期;不做定时清扫(Desktop 102GB 事故 #29388 的反面教训)。*(修订:留了一个有界的例外——工作区最近 20 条恢复记录跨会话保留,否则关掉 codex 就等于悄悄解除了刚做的回退的后悔药。)*
    - **[重申 · 2026-08-11]** 讨论过"照搬 Claude Code 的 100 条快照上限"(按线程保留最近 N 轮,更早的裁掉),**否决**。理由是你提的:**不设轮次上限本身就是一种设计哲学,和 git 一致,不需要照搬 Claude Code。**
    - **我们本来就已经是 git 的形状**。git 从不按年龄或数量截断历史,`git gc` 只清理**不可达**的对象;我们的 mark-and-sweep 也是同一条规则——从线程日志、turn 索引、恢复栈三组根出发标记,会话被删时它的捕获才成为垃圾。**保留与否由可达性决定,不由数字决定。**
    - **为什么 Claude Code 的 100 不可移植**:它存的是**逐文件副本**,成本 ≈ 快照数 × 变更文件数,数量上限确实是那个模型里最自然的界。我们是内容寻址,blob 天然去重,成本结构完全不同——把一个不同存储模型下的策略常数搬过来,搬的是数字,不是理由。
    - **而且它会和决策 11 自身冲突**:RFC §8 明确否决 `shell_snapshots` 那套 3 天定时清扫,理由是"**会让还可能被合法引用的状态自行消失**"(对老 fork 的恢复直接失效)。轮次上限是同一个失败形态的另一种写法——`/rewind` 的选择器是从**对话**里列出来的,不是从快照日志里,所以被裁掉的那些轮次**照样会显示在菜单里**,用户点下去才发现回不去。
    - **将来体积真成问题时的正确方向是"压缩,而不是遗忘"**:这也正是 git 的答案(packfile + delta),不是截断。manifest 可以 delta 编码或压缩,blob 层的 CDC 接口 RFC 里已经预留(§11 待办 4)。这条路与本决策同向,上限那条不是。
    - **不要改回**:"跟 Claude Code 一样加个 100 就行了"是个非常自然的建议,大概率还会被再次提出。否决它的不是嫌麻烦,是上面那三条。
20. **回退必须幂等,且与分支无关**(用户要求:"这个肯定要幂等啊,不能因为 redo 状态改变而改变")。落地为两条绑定的改写:快照按 **turn id 全局索引**(turn id 在 fork 时逐字复制,任何分支问同一个 turn 都得到同一答案),redo 目标按 **工作区**记录(而不是记在执行回退的那个线程上)。恢复计划退化成"比较目标与现状两个 manifest",不再回溯历史——历史一旦参与计算,答案就会随所在分支漂移。
    - **[部分修订 · 2026-08-11]** turn id 全局索引和"不回溯历史"这两条**保持不变**;redo 目标的键从"工作区"改成"**切换到的目标线程**",见决策 24。当初否决"绑线程"时否的是绑**源**线程(rewind 之后用户已不在其中),这个理由仍然成立——但工作区不是唯一的替代品,而且它是共享的。

24. **undo 记录按"切换到的那个 session"归档,每个 session 一个栈,不共享**(你提出)。
    - 这是决策 20 的**修订**:那条把 redo 目标从"执行回退的线程"改成"工作区",理由是线程会分叉、记录会失联——**这半个判断仍然成立**。错的是替代方案:工作区虽然可达,却是**共享**的,同一目录并发两个会话就会压在同一个栈上,谁先撤销谁就花掉了对方的记录。
    - 正确的键是**目标线程**,即 rewind 切换到的那条分支。它同时满足两个条件:**可达**(用户按 `/redo` 时人就在里面)和**私有**(别的会话够不到)。绑源线程只满足私有,绑工作区只满足可达。
    - 顺带删掉了 `undo_files_restore` 里的 `thread_exists` 门禁——它检查的是"调用方有没有快照",两个并发会话都满足,从来就防不住这件事。真正的门禁变成"这条线程有没有自己的记录"。
    - **一个推论**:回退到第一条提示词时对话是**重开**而非分叉,没有目标线程可归档,因此**不压栈、不可 redo**。这与决策 23 的确认对话框正好吻合,文案相应简化为"`/redo` 无法撤销这一次"。
    - **未解决的那一半**:文件仍然是共享资源。并发会话各自撤销时,仍会覆盖对方的工作——记账解决不了。留在 RFC §11,建议的解法是撤销前用 `target_manifest_id` 比对工作区现状,发现被动过就询问而非直接执行。

25. **覆盖检测放在客户端,协议零增量**(你追问"前面几个确认弹窗是怎么设计的?能不能参考"逼出来的)。
    - 决策 24 让 undo 记录变私有,但**文件仍是共享的** —— 两个会话改同一批文件时,一方 redo 仍会覆盖另一方的工作,而且**静默**。实测复现:python 写 `B1`,markdown `/redo` 后变成 `A2`,`B1` 只剩在 blob 库里够不着。
    - 检测本身没有歧义:restore 记录里的 `target_manifest_id` 就是"这次 rewind 把工作区变成了什么样",逐条读现状算 hash 比对即可。**坚持真读真算而不走 stat cache 快路径** —— 快路径会漏掉同 tick 内的等长改写,而在这里误判成"没变"的代价正是静默覆盖别人的工作。比对范围只有恢复会碰的那几个路径,成本可以接受。
    - **争议在放哪。** 我先后提了两个都往协议里加东西的方案:A(新增 `thread/undoFileRestorePreview`)、B(给现有请求加 `force` 参数)。都被否了,因为**前两个确认框(决策 21c、23)本来就是纯 TUI 判断,零协议改动** —— 提交 `56304755a1` 只碰了 4 个 TUI 文件。
    - 正确做法是延续既有模式:**"该不该问用户"是呈现层的事**,服务端只负责执行。不同客户端(IDE、Desktop)可以问得不一样,甚至不问。TUI 早就依赖 `codex-file-snapshots`(`/status` 显示磁盘占用时直接开 store),所以检测就在本地读一次,不需要往返、不需要重新生成 schema。
    - **这一条在这个项目里权重格外高**:codex 的 `ClientRequest` 是封闭 enum,`ext/extension-api` 只提供生命周期钩子、**不能贡献协议方法**。所以每加一个方法都是对上游文件的永久改动,而协议层是我们唯一无法解耦的地方(自己的 crate 3698 行完全独立,协议+app-server 却有 351 行刻在上游文件里)。
    - 路由顺序抽成了纯函数 `redo_prompt`:**冲突优先于"回退后又干活"** —— 覆盖别人的改动既不可见又不可恢复,而丢弃的轮次至少还在 transcript 里看得到。

12. **显式配置开启(opt-in)+ 磁盘占用披露**:不需要该功能或磁盘紧张的用户各取所需。
13. **砍掉不必要的复杂度**:只保留"`/status` 显示用量"和"未开启时 backtrack 界面的发现性提示";空间上限、清除命令等不做,需要时再加。

21b. **redo 的对话来源改为快照库自存的副本,而不是把归档的线程移回来**(你提出)。rewind 时把源 rollout 整个存进 blob,记在 restore 记录里;redo 用 `thread/fork.path` 从这份副本**新建**一条对话。这样一来"归档文件被外部移动/删除"和"原线程后来又前进了"两种情况同时消失——undo 不再依赖任何会变的外部产物。
    - 代价:rollout 是整文件哈希,存不了增量,每次 rewind 一份全量副本(实测一次短会话 212K)。用与 restore 栈相同的封顶 + GC 约束。rollout 是**只追加**文件,正是 CDC 的理想场景,RFC 里留的接口将来能近乎完美去重。
    - 后果:redo 产出**新的 thread id**,不再复活原线程。换来的是 rewind 与 redo **对称**——两者都是"从记录点 fork,归档离开的那条",不再有 unarchive 这条会失败的路径。
    - **[已推翻 · 2026-08-11]** 改回 unarchive 原线程。
    - 推翻理由(实测撞上):**turn id 是运行时标识,不写进 rollout**。从 rollout 重建的线程会被分配**全新的 turn id**,而所有快照都按旧 id 索引——于是 redo 之后的第一次 rewind 解析不到任何快照,**对话回退了、文件纹丝不动,而且不报错**。这比副本要解决的问题严重得多:它破坏的正是决策 20 赖以成立的那个 join key。
    - 副本原本防的是"归档被外部移动/删除"和"原线程又前进了"。后者**结构上不可能**:`find_thread_path_by_id_str` 默认只搜 `sessions/`,归档区要另一个函数,而它只被 `/archive` 管理命令调用——归档即冻结。前者仍可能(用户手动删除),现在的处理是**报错而非静默半途而废**:文件照常恢复,当前线程保持不动。
    - **不要改回**:"自存副本更独立、少依赖外部产物"这个论证本身没错,错在它牺牲了 turn id 的连续性。除非 turn id 进了 rollout(那要动持久化格式,违背决策 15),否则重建对话这条路都不成立。
21c. **"rewind 后又干了活再 redo"用确认对话框解决**(你提出)。redo 回到的是 rewind 那一刻,期间的工作会被一并撤销;数据仍在(归档的 rollout + 被 turn 索引 pin 住的快照),但没有命令能走回去,所以问题是**可达性**而非丢失。现在按 `TurnStarted` 计数,>0 时弹确认并说明会丢弃几轮。
    - 一个澄清让这个问题变简单了:**归档的那条不可能前进**。`find_thread_path_by_id_str` 默认只搜 `sessions/`,归档区要另一个函数,而它只被 `/archive` 管理命令调用——所以任意时刻只有一条活跃线路,不存在双向分叉,只需处理"活跃这条前进了"。
    - **[限定 · 2026-08-11]** 上面这条只在**单会话**内成立。同一工作区并发多个会话时,undo 栈是**按工作区共享**的(决策 20 的直接后果),而 `RestoreRecord` 里没有执行者身份——A 的 `/redo` 会弹掉 B 压的记录。`undo_files_restore` 里的 `thread_exists` 门禁**防不住这个**:它只检查"调用方有没有快照",两个会话都满足。详见 RFC §11 开放问题。

21. **回退对用户呈现为"同一条对话",不暴露分支**(用户:"用户很难理解和使用分支……分支会一直增殖,既然回退了一般对用户来说这个就没啥意义,有 redo 兜底就足够了")。底层仍是保源 fork——这正是 redo 能回去的前提——但被取代的线程在切换时归档,会话列表里始终只有一条在延续的对话,`/redo` 把两者换回来。注意这是**客户端呈现选择**而非协议改动:协议层依旧是分支形状,想展示分支的客户端仍可展示。
    - 备选方案 `thread/rollback`(真正的原地截断)已被上游标记 DEPRECATED("will be removed soon"),因此不能作为地基。

### 持久化
14b. **追踪标记惰性创建**(实测发现):日志由**第一次 checkpoint** 写,不在会话启动时写。codex 每次启动 TUI 都会分配一个 thread id,若用户随即 resume 别的会话或退出,这个 id 就被废弃——它的 rollout 也正因如此是惰性创建的。我们急切落标记,结果成了唯一会留垃圾的组件(开发机上超过一半的日志是空的)。改成惰性**不损失任何信息**:标记唯一要回答的问题是"这个会话有没有快照",而没有快照的会话,resume 时算开算关都没有区别。
    - 顺带修正了语义:标记的含义从"这个会话启用了追踪"精确成"**这个会话有快照**"。

15. **与现有持久化完全分离**:不给 rollout/TurnContextItem 加任何字段;快照子系统自己的日志**反向引用** rollout 的 turn id。追踪开关状态 = 快照日志文件是否存在(连 boolean 字段都不用加)。此决策一次性拆除了三颗协议雷(TurnContextItem 去重陷阱、legacy ghost_snapshot 清洗器、fork 截断边界 off-by-one)。

29. **三个"文档说了意图、没说不变量"的实现缺陷,以及由此加的构造侧规则**(2026-08-11,你要求专门审计文档才挖出来的)。
    - 三个 bug:① git 分区在仓库**子目录**会话里恒为空(`gix::open` 不向上找);② `path.is_file()` 把"索引里有、磁盘上没有"的文件提前丢掉,于是**没有墓碑**,删掉又建回来的文件回退时删不掉;③ 第三分区的 100 个名额在去重**之前**就花在了重复项上。
    - **共同点比三个 bug 本身重要**:RFC §7 原来的六条正确性规则**全部约束恢复侧**,没有一条约束"追踪集合怎么构造"——而三个 bug 全在构造侧。**三个错误实现都满足 §7 的每一条。**
    - 因此 §7 补了四条**构造侧**规则,并且写成可检验的性质而不是意图:
      7. **枚举只负责提出候选,存在与否只由 capture 判定**——被枚举却没找到,那是**证据**(墓碑),提前过滤等于把删除依据扔了。
      8. **第三分区是残差,预算只花在另外两个之外**,而且排除发生在**排序之前**。
      9. **一个文件只能有一种拼写**(锚定在会话的 root 上)——manifest 的 key 是绝对路径字符串,两种拼写就是两个条目。
      10. **会话内只增不减**。
    - 另外把"两个调用点为什么安全"的真实理由写进了 §7 和代码注释:**不是**因为两边输入一致(它们三个参数全不一样),而是因为 `plan_restore` 只能写 `target.entries`、只能删 `target.absent`,而安全侧拿到的是整条线程的历史,恰好是这两个集合的并集的超集。**谁把这个历史收窄,谁就在不碰恢复代码的情况下弄坏了可撤销性。**
    - **[附带发现]** RFC 里引用的所有测量数字,当初都是在**仓库根**、且三个 bug 都在的情况下测的——所以文档自己的证据和错误的实现完全自洽。以后引用数字要注明测量位置。

    - `forget_threads` 刻意**不可失败**:删对话不能因为快照清理失败而失败,所以错误只记日志,调用方一行、零错误处理。
    - 两个必须同时做对的地方:
      - **删日志只是忘记的一半**。undo 记录在另一个文件、另一套生命周期(rewind 把它归档在**切换到**的那条线程下,那条线程可能自己还没有日志),而且它**本身就是 GC 根**。留着它就会永久钉住它命名的 manifest——实测那个真实仓库里 73 个 manifest 有 37 个只能靠一条**已经用掉的** undo 记录到达。
      - **清扫需要一个并发答案**,因为这是它第一次真的运行。capture 是三步发布(blob → manifest → 日志条目),不是原子的;先读日志、后列文件的清扫会删掉活跃会话认为自己持有的快照。通用清扫因此**放过最近几分钟内写入的一切**,和 git 的 `gc.pruneExpire` 同一个答案:回收延迟,但什么都不会丢。
    - **但只有宽限期会把这个功能本身废掉**——刚聊完就删的对话什么都回收不了,而清扫只在删除时运行,"以后"可能等于"永远"。测试当场把这个抓出来了。所以删除路径改为**精确清扫**:先读出这些线程命名了哪些 manifest,再删日志,只考虑这批候选。活跃会话正在发布的东西**永远不会成为候选**,所以这条路径不需要宽限期,立即回收。仍被其他线程引用的照常保留(fork 之间共享 manifest)。

32. **undo 的删除覆盖:从"靠调用方传够"改成"构造上充分"**(审计 + 你要求进一步分析后确认的真 bug)。
    - **现象**:`/redo` 会**静默地漏删**一个本该删掉的文件。而且覆盖检测也不会提示——它比对的是 `record.target_manifest_id`(rewind 的目标),不是安全快照,那个路径在它检查的集合里根本不存在。
    - **机制**:删除要求 `path ∈ target.absent` **且** `path ∈ current.entries`。undo 记录归档在**切换到的那条分叉线程**下(决策 24),而 `inherit_log` 只复制到分叉那一轮为止——所以分叉线程的历史里**既没有安全 manifest,也没有源线程分叉之后学到的任何东西**。于是安全快照里明明写着墓碑,redo 的扫描清单里却没有这个路径,第二个条件不成立,文件留下。
    - **为什么这么窄**(三条显而易见的路都是自己堵死的):rewind 自己恢复出来的文件必在 `target.entries` 里,而那一轮**恰好**被继承;edit 工具新建的文件会往分叉线程自己的日志里写墓碑;git 索引里的文件两头都拿得到。**剩下的必须是 rewind 之外的东西**(shell、编辑器、并发会话)把文件放回磁盘,而且路径要在工作目录之外/隐藏/在跳过目录里。
    - **修法不是去补分叉继承了什么**,而是换个问法:这次恢复到底可能碰哪些路径?**只有 `target.entries` 和 `target.absent`**。那就把这两个集合直接并进安全捕获的清单——**墓碑自己把自己捞回清单**。
    - 三个好处:① 直接修好;② 只增不减,现有行为一律不变;③ **让一条脆弱的不变量退休**——就是两个 commit 前刚写进文档的"任何人都不许收窄 `tracked_paths`"。充分性从此是**代码的性质**,不再是**关于调用方的论证**。放在 `restore_to` 里面而不是调用点,三条路径自动获得。
    - 回归测试**已验证"去掉修复就必然失败"**。
    - RFC §7 因此加了第 11 条,并把原来那段"靠整条历史"的说明**保留下来**、注明它为什么不成立——因为它看起来很有道理,很容易被重新写回去。

33. **回退越早恢复越少的反直觉,用一句话告诉用户该怎么办**(你提出的)。
    - **现象**:回退到第 3 轮能把某个文件恢复回来,回退到**更早**的第 2 轮反而不能。
    - **根因**:追踪是**被发现**出来的,不能追溯。工作目录**以内**的文件每轮都会被重新枚举,所以每一轮都认识它们,单调性正常;**以外**的文件只有在 edit 钩子第一次碰到它时才进入系统,所以更早的那一轮**确实没有**这个文件的任何记录,也就没有内容可以写回。
    - **当前行为是对的那一侧**:没有证据就不动手。拿第 3 轮的 pre-image 去冒充第 2 轮的内容写回磁盘,是在写一份来历不明的字节;而"沿历史往后找一份 pre-image"这条路决策 20 已经砍过了(会让恢复随分支漂移,幂等性没了)。
    - **所以这不是机制问题,是没告诉用户的问题**。用户以为"回到第 2 轮 = 回到第 2 轮的样子",实际是"回到第 2 轮时**系统知道的那部分**的样子",差在哪儿他看不见。
    - 落地:rewind 之后加一行提示,**并且直接说该怎么办**(你的要求:"不然用户不明白提示什么意思")——「N 个工作目录外的文件在这一轮还没有被追踪,保持原样未动」+「回退到更近的一条提示词可以恢复它们」。纯 TUI 判断,读本地 store,**零协议改动**(决策 25)。判据本身 `unrestorable_outside` 放在 crate 里,可单测。

34. **覆盖警告要读两张 manifest,因为它们回答的是不同问题**(你的决定)。
    - 修复 32 让 redo 会删掉安全快照标记为 absent 的路径——**删对了**,但警告没跟上:它只读 `record.target_manifest_id`(rewind 的目标)。
    - 两张 manifest 的分工:**rewind 的目标**说的是"rewind 把工作区留成了什么样",所以它能抓到"之后有人改过";**安全快照**才是"undo 要恢复到哪",所以只有它知道"这个文件当时不存在、现在存在、马上要被删"。
    - 只读前者,漏掉的正好是用户最想被拦下来的那种:**自己在 rewind 之后新建的文件,被静默删除**。现在两张都读,结果去重。
    - 文案同步改成"替换或移除",因为删除比覆盖更重,不能藏在"overwrite"这个词里。

35. **读不了/非普通文件:跳过,不记录,不修**(你判断的,理由是 git 也这么做)。
    - `capture` 对每个路径 stat 一次,结果有**三个**去向:进 `entries`、进 `absent`(墓碑)、或者**哪儿都不进**(读不了、或不是普通文件——目录、符号链接),只给 `stats.skipped` 加一。第三种在 manifest 里不留任何痕迹,对恢复两个方向都隐形。
    - 同意跳过。不过检查时发现一个**窄的硬失败**,记在这里备查:**同名文件↔目录互换**。第 1 轮 `foo` 是文件(有 entry),之后被换成同名目录 → 捕获时 `!is_file()` 跳过、不留记录 → 回退到第 1 轮时 `plan_restore` 要写 `foo`,而 `apply_plan` 是 `fs::rename(tmp, foo)`,**rename 到已存在的目录会失败**,错误上抛,**整次恢复中止**。不是数据丢失,是硬报错;要文件/目录同名互换才触发,罕见。

36. **并发会话不再投入**(你的决定):一般人用 worktree 或多 repo,为一份共享工作区的并发会话做合并会让问题过于复杂。
    - **但决策 25 那套检测不拆**:它在单会话下同样有用——用户在 rewind 和 redo 之间用自己的编辑器改了文件,是完全一样的场景。所以是"不再往这个方向投入",不是"那段代码白写了"。

37. **安全 manifest 被已花掉的记录永久钉住:量化之后决定暂不修**(你的决定)。
    - **机制**(两个 GC 根,弹栈只松开其中一个):
      - `restore_to` 拍安全快照走的是普通 `checkpoint()`,而它做**两件事**——往 `refs/<线程>.json` 追加一条 `{turn_id: "safety-restore:<id>", manifest_id}`,**并且**往 turn 索引写 `turns/safety-restore_<hash>`。
      - `pop_restore`(撤销被花掉时)**只改写 `restores/`**。`refs/` 是只追加的,而且 `inherit_log` 按位置切分它,中间抽条目有风险;turn 索引同理。
      - 于是撤销花掉之后,那张安全 manifest **仍被 `refs/` 那条钉着**,而 GC 正是从 `refs/` 标记。
    - **回收时机**:**只有整条对话被删除时**,没有第二个触发点(`gc()` 目前唯一的生产调用者就是删对话)。也就是说——**这张 manifest 活得和对话一样久**。
    - **量化**(实测每条目 **254 字节** = 固定 198 + 路径长度):

      | 项目规模 | 每张全量 manifest | 每次 rewind 的永久成本 |
      |---|---|---|
      | codex 仓库(6,096 文件) | ~1.5 MB | 1.5 MB |
      | 中型项目(1,500 文件) | ~0.3 MB | 0.3 MB |

      blob 那部分≈0:安全快照拍的时候绝大多数内容早已在库里(内容寻址去重),只有真正变过的才是新 blob。
    - **审计报的「38/76 = 50%」有误导性,别被它吓到**:那个 store 全是**短对话 + 高频 rewind** 的测试数据(三五轮的对话却 rewind 好几次)。真实使用里轮次远多于 rewind,每个普通轮次也都是一张同样大小的全量 manifest,所以这些安全 manifest 大概只占 5–10%。**主要成本是轮次 manifest,而那些不是垃圾。**
    - **决定:先记结论,不改动。** 理由:① 正常使用下影响是个位数百分比;② 唯一的触发点(删对话)已经工作正常(`1551ee896c`),手工清理也验证过 1472 KB → 80 KB;③ 真正的理由从来不是省空间,而是"**一条已经花掉的记录留下一个永久 GC 根**"在概念上不干净、让 store 难以推理——但这不值得为它单独引入一次行为变化。
    - **将来要修的话,方案 (c) 记在这里**:安全 manifest **不写进 `refs/`**,只由 restore 记录引用。`restores/` 本来就已经是 GC 根,所以 `pop_restore` 一弹,它自然变成垃圾、自动回收,不需要任何新机制。顺带 `latest_manifest` 会回到上一个**真实轮次**,stat cache 和 `attach_pre_edit` 的基准都更合理(安全快照描述的是一个即将被覆盖的状态,拿它当缓存基准本来就怪)。
    - **(c) 的连带行为变化,是它不该被顺手夹带的原因**:redo **自己**也会拍一张安全快照(内容是"被 redo 覆盖掉的那份工作")。它现在只存在于 `refs/`,改完之后将不被任何东西引用——也就是从「**够不着但还在**」变成「**可回收**」。2026-08-11 那次 `shared_outer.txt` 测试里的 `B1` 就是这份数据,当时是从 blob 库里手工读出来的。要不要放弃这条无人知晓的抢救退路,是个**独立的产品决定**。
    - **明确否决的做法**:让 redo 也**压栈**(即允许"撤销 redo")。它看起来能把 `B1` 救回来,但那正是**决策 9 修订否决过的形态**——文件会在两个状态之间来回跳,而对话却一直在往回走。不要改回。
    - **什么时候重新捡起来**:有人真的抱怨 store 体积,或者要给 GC 加第二个触发点(比如会话启动时清扫)的时候。那时 (c) 是顺理成章的一部分,而不是一个孤立的改动。

39. **覆盖警告要按 `safety` 而不是 `target` 枚举「会被动到的东西」**(你实测追问出来的,决策 34 的补完)。

### 平台差异与存储正确性(2026-08-31,一轮 CI + 覆盖率审计带出来的)

42. **路径一旦变成 `String`,平台差异就开始咬人;变成 `PathBuf` 就不咬。** 这一条是下面好几个 bug 的共同根因,单独列出来。
    - `Path`/`PathBuf` 的 `Eq`/`Ord` 是**按 component 比**的,Windows 上 `/` 和 `\\` 等价。所以 `tracked_files` 的 `BTreeSet<PathBuf>` 会正确合并两种拼写,**不会**产生重复条目。
    - 但 manifest 的 key 是 `path.to_string_lossy()`——**原始字符串**。所以同一个文件的 key 取决于**哪个分区先找到它**,而下游所有 `contains_key` / `contains` 都是字符串比较。
    - **不要改回**:不要用"`PathBuf` 比较过了所以没问题"来结束分析。要问的是"**这个值后面会不会变成字符串**"。
    - 连带教训:**断言 `Vec<PathBuf>` 相等的测试,结构上看不见分隔符**。要验分隔符必须断言 `to_string_lossy()`。这类断言在 Unix 上是恒真式,存在的意义**只在 Windows 那条腿上**——写的时候要在注释里说清楚,否则以后有人会当成冗余删掉。

43. **git index 永远是 `/` 分隔,和平台无关。** 这条踩了两次,两处都在 `scope.rs::git_tracked_files`。
    - **上游那半**:用 `relative.to_string_lossy()` 拼前缀去查 `prefixed_entries`。Windows 上深度 ≥2 的会话根产生 `app\\deep/`,和索引里的 `app/deep/...` 匹配不上 → 返回 `None` → **git 分区静默返回空**,快照只剩另外两个分区兜底。修法:用 `components()` 拼 `/`。
    - **下游那半**:`root.join(rel)`。`Path::join` 只插入**一个**原生分隔符,后面的字符串**原样拷贝**,所以索引里的 `/` 会活到结果里:`C:\\repo\\src/main.rs`。修法:`rel.split('/').fold(root, |acc, c| acc.join(c))`。
    - 下游那半的后果比看起来重:manifest 里同一个文件出现两个 key,`plan_restore` 为每个 key 各发一次写入,而 BTreeMap 序下 `/`(0x2F)排在 `\\`(0x5C)**前面**——于是**编辑前的旧内容后写、赢在磁盘上**,正好把 `attach_pre_edit` 短路要保证的规则颠倒过来。
    - **为什么测试没抓到**:唯一相关的测试只走了**一层**子目录(`repo/app`),而一层的 relative 里根本没有分隔符。差一层。
    - **不要改回**:任何"把路径拼成一个字符串再交给 git"的写法。索引的分隔符和平台的分隔符是两件事。

44. **`Gitignore::matched_path_or_any_parents` 在路径不在其 root 之下时会 panic**(文档明写)。空 matcher 会提前返回,所以只有工作区**有非空 `.codexsnapignore`** 时才触发。
    - 触发点是编辑钩子:它收到的是 agent 实际写入的**绝对路径**,不保证在会话根之下。panic 会中断整批 pre-image 循环,丢掉的正是 `absent` 墓碑——而墓碑是"允许 rewind 删除 agent 新建文件"的唯一凭据。`events.rs` 丢弃了 JoinHandle,所以这一轮会当作一切正常继续。
    - 修在 `is_ignored` 里做边界检查,不在调用点——因为 `tui/src/chatwidget.rs` 用 `config.cwd` 建 matcher,有同样的暴露面。
    - **越界路径答"不忽略"是语义正确,不只是安全**:这套规则描述的是一个目录,对目录外的东西无可奉告;而 agent 在工作区外新建文件的墓碑,正是之后允许删除它的唯一依据。
    - **不要改回**:不要用 `catch_unwind` 包,也不要只在单个 primary root 上预检查——后者会漏掉决策 45。

45. **多 workspace root 时,每个 root 的 `.codexsnapignore` 都必须生效。** 原实现 `ignore_root: Option<PathBuf>` 只取 `roots.first()`,于是第二个 root 里的排除规则对该 root 内的编辑完全无效。
    - 为什么没有下游兜底:**恢复侧的对称忽略是结构性达成的**——`restore.rs`/`store.rs` 里没有任何地方查 `is_ignored`。所以一个路径只要漏进 manifest,rewind 就会把它写回来,墓碑还会允许删它。**漏进去就是全部的失败**。
    - 改成 `ignore_roots: Vec<PathBuf>`。

46. **`already_known` 也必须过 ignore 过滤。** `tracked_files` 原本把它直接 collect 进集合,两个分区循环之后才应用 matcher。后果:一个文件在被加进 `.codexsnapignore` **之前**进过会话,之后每一轮都会被交回来继续快照——而规则 5 说的是以**当前**的 ignore 文件为准。恢复侧经由 `thread_processor.rs` 传入 `tracked_paths` 也是同一条路。
    - **过滤时的硬约束**:不在任何 root 之下的路径**必须保留**,否则会破坏"工作区外新建的文件能被 rewind 删掉"。修好后的 `is_ignored`(决策 44)对越界路径返回 false,这条约束自动满足。

47. **blob 并发写入用无锁的唯一临时名,不用队列/文件锁。**
    - 原实现临时名是 `<内容哈希>.tmp`,完全由内容决定,两个共享 `CODEX_HOME` 的进程会撞同一个临时路径。
    - **为什么不串行化**:进程内 Mutex 解决不了跨进程;跨进程文件锁要引依赖(workspace 里没有,现有两处 `flock` 都是 Linux-only 的裸 libc 调用)、要处理崩溃后的陈旧锁、还要让一次 capture 的几十上百次写入排队。
    - **而内容寻址让协调变得不必要**:哈希相同就是内容相同,两个写入者写的是同样的字节,不存在"谁赢"的问题,只需要它们别共用临时文件。这是 git 自己的做法。
    - 命名用 `<hash>.<pid>.<counter>.tmp`——**`.tmp` 必须留在最后**,因为 `hashes()` 靠后缀识别在途文件。分诊最初建议的 `<hash>.tmp.<pid>` 会破坏这个过滤。
    - 附带修掉:rename 失败但目标已存在时视为成功(Windows 上目标被读者打开就会走这条路)。

48. **`hashes()` 会把目录里任何非 `.tmp` 文件读成 blob 哈希。** macOS 的 `.DS_Store` 就足以触发:它变成假哈希 `b0.DS_Store`,过了宽限期 GC 就把它删了——**扫描器在删自己没创建的文件,依据是自己编造的名字**。加十六进制校验。

49. **死代码清理(三处,均 grep 确认零调用者)**:`find_workspace_root`(决策 5 那次重构后失去全部调用者,`pub` 所以 `dead_code` 不响、`cargo shear` 只查依赖不查导出)、`TurnIndex::restore_logs`、`BlobStore::store_file`。另把 `RefStore::log_path` 里逐字重复的 sanitizer 收敛到 `safe_file_name`——两份拼写各自漂移的话,同一个线程的日志和 restore log 会 key 到不同文件名。

50. **测试的 hermeticity:向上无界的 walk 不能断言"找不到"。** `find_workspace_root` 的否定用例从自己的 tempdir 出发向上走,断言找不到 `.codex`——这是关于**机器**的断言而不是关于代码的,在 `/tmp/.codex` 存在的机器上直接红。该函数随决策 49 一并删除,问题消失;但这个陷阱形态要记住。

### 恢复安全性与平台审计(2026-08-31,同一轮的第二批)

51. **恢复的临时文件必须独占创建(`O_EXCL`),不能跟随符号链接。**
    - 原实现名字是固定的 `<文件名>.codex-restore-tmp`,用 `fs::write` 写——而 `fs::write` 展开是 `open(O_WRONLY|O_CREAT|O_TRUNC)`,**跟随符号链接**。工作区里预置一个同名符链,恢复的内容就写到链接指向的地方,工作区外也一样。
    - **不需要"先攻进机器"**:agent 自己能创建它(而 agent 正是 rewind 要撤销的东西),崩溃的恢复会留下它,而且**一个 clone 下来的仓库可以直接带着它** —— 这是供应链向量。
    - 修法:`File::create_new`(`O_CREAT|O_EXCL`),遇到已存在的路径**失败**而不是跟随;名字加 pid+counter。
    - **测试要点**:名字随机化之后,测试**无法**在真实恢复会用的路径上预置任何东西——这正是随机化的意义,也因此保证必须在别处钉住。为此抽出 `write_exclusive(tmp, content)` 接缝直接测拒绝行为。第一版测试就是栽在这里:在测试里调 `tmp_path` 会推进计数器,种的链接和实际用的路径对不上,测了个寂寞。
    - 相关但**决定不做**的:blob 加载时校验哈希、manifest/日志哈希链。内容寻址已经把完整性原语给了(文件名就是内容的 SHA-256),但 `load` 从不复验。判断:哈希链防的是"落点正确、内容被篡改",和本条(内容正确、落点被劫持)**正交**,修不了本条;而链的信任根本身也要保护,能写 `~/.codex` 的攻击者通常也能写你的 shell 配置。**除非快照目录会同步到网盘/共享存储**,否则成本高、边界收益低。

52. **`apply_plan` 永不中途放弃。** 一个中途失败的恢复比一个完全失败的恢复更糟:undo 记录是调用方在 `apply_plan` 返回**之后**才写的,所以提前 `?` 会留下"写入落了一部分、删除落了一部分、且无法撤销"。
    - 改成收集 `ApplyStats.failed: Vec<(路径, 原因)>`,跑完整个循环,undo 记录**无论如何**落盘,再把没能恢复的文件告诉用户。
    - Windows 上这是常态而非异常:编辑器打开的文件无法被替换,只读**属性**直接挡住删除(Unix 看的是目录权限)。

53. **pre-edit 镜像必须记录真实权限位。** 原来硬编码 `0o644`,注释的理由是"补丁内容没有 stat 可用"——**这话只对"内容"成立**。钩子在编辑发生**前**运行,文件还在磁盘上,权限读得到。
    - 后果:agent 编辑过一个脚本,rewind 回去时**恢复了字节、同时把可执行位 chmod 掉了**。四个独立的审计视角各自发现了这一条。
    - 用 `symlink_metadata` 而非 `metadata`:符号链接自身的 mode 和恢复要写的文件无关,capture 也是同样理由跳过链接。

54. **ignore 匹配要跟随文件系统的大小写语义。** NTFS 和 APFS 默认大小写不敏感,而 `GitignoreBuilder` 默认大小写敏感,于是规则 `secrets/**` 盖不住 `SECRETS/key.pem` —— 而操作系统认为它们是同一个目录。git 出于同样理由做同样的调整(`core.ignorecase`)。
    - 按**平台**判断而不是探测:macOS 的卷**可以**格式化成大小写敏感,但在那里过度忽略的代价只是"刻意区分大小写的一对文件被多忽略了";**漏忽略才是会泄漏的方向**。

55. **矛盾的证据不是删除许可。** 同一个文件若以两种拼写进了 manifest(APFS/NTFS 的大小写、来自 git 索引的分隔符),就可能**同时**持有内容记录和墓碑。`apply_plan` 先写后删,于是 rewind 会把文件恢复出来再删掉——比单独任何一半都糟。
    - 加不变量:**`target.entries` 里有的路径永不删除**,不管 `absent` 怎么说。这条护栏不依赖别名的来源,大小写、分隔符还是别的什么都能挡。

56. **非 UTF-8 文件名在捕获时跳过并 warn。** manifest 的 key 是 `String`,lossy 转换会产生 U+FFFD,恢复时会**创建一个乱码兄弟文件而真文件从头到尾没被碰过**。不快照是诚实的结果:没恢复可以补救,恢复到错的路径不能。改成存原始字节要动持久化格式,为一个罕见情形不值。

57. **`all_restore_logs` 改为 `.json` 过滤 + fail-closed。** 原来它跳过任何读不了或解析不了的文件,**看起来像容错,实际是漏了扩展名过滤然后用宽松错误处理盖住了症状**——`write_atomic` 是 rename 落地的,崩溃只会留下 `.tmp`,不会留下半截的 `.json`。
    - 代价对比:GC 失败会重试;因为读不了 GC 根而被删掉的快照没了。现在和 `thread_logs`、`retain_turns`、`BlobStore::hashes` 是同一个形状:**残片按扩展名跳过,其余一律传播**。

58. **测试与平台的两条元教训。**
    - **只在某一个平台上有意义的断言,不能因为看着冗余就删。** `git_tracked_files` 那条字符串断言在 Unix 上是恒真式;2026-08-31 用一个只含测试、不含修复的临时分支实测,Windows 那条腿**变红**,ubuntu 和 macOS **绿**——对照组证明了测试没写错,红的是真 bug。构造性论证之外,这是唯一的实证途径。
    - **`cargo test` 发现不了 CI 会红的东西。** 这一轮 clippy 在测试全绿的情况下抓出 9 处:删函数后遗留的 import、6 处 redundant clone、被吃掉的 `#[test]` 属性、以及本 crate 禁用的 `expect`。改完必须跑 `cargo clippy --all-targets -- -D warnings`,不能只跑测试。

### 上游同步 rust-v0.147.0 → rust-v0.151.0(2026-08-31)

## 三、关键澄清时刻(对设计影响最大的几次质疑)

1. **"Esc 中断自动回退和代码回退没关系吧?"** —— 对。核实代码:该路径只回对话,且只要出现过任何 `tool_use` 块就不触发,结构上不存在"有文件改动却自动回退"的情况。修正了此前不严谨的表述。
2. **"git 对 untracked 在回退时也不会变,为什么要删?"** —— 澄清了 agent-rewind 语义 ≠ git checkout 语义:agent 新建的文件若不删,回退就是"半个回退"(对话说没发生过,磁盘说发生了)。配合"恢复前安全 checkpoint",删除永远可恢复,旧方案的记账问题整体消解。
3. **"快照延迟不懂,git 明明很快?"** —— 澄清 ghost-commit 慢的真因:出于安全不敢碰用户 index,改用一次性临时 index,从而**丧失了 git 快的根源(持久 stat cache)**。自建 stat cache 正是把这个速度来源拿回来且无安全冲突——所以它是必选项不是优化项。
4. **"持久化分离不难吧,让快照引用现有历史 id 就行?"** —— 对,且严格优于原 RFC 方案(决策 15)。Phase 3 工期估算从 ~1 周降到 3–5 天。
5. **redo 与"目击出生"规则的冲突**(实现中发现):被恢复重建的文件永远受目击出生保护,导致 redo 不完整。修正:manifest 增加 `complete` 标志,全量扫描的缺席是确凿证据可直接删除(决策 10 的精化)。这个洞在设计文档层面不可见,是"先做原型"价值的直接证明。
   - **[后续 · 2026-08-11]** `complete` 已删除(决策 10 四次修订)。但这条记录**要留着**,因为它的教训还在:当时之所以要引入 `complete`,是因为"目击出生"这条规则**记的是历史而不是状态**。真正治本的是决策 20 拆掉历史回溯、决策 10 三次修订换成墓碑——`complete` 只是这中间的过渡。教训不变:**删除依据必须是一次具体的观察,不能是一个全称断言**;全称断言总要有人去维护它的前提,而前提总会在某条路径上不成立。
6. **"rewind 不起作用了 / redo 没问题但 rewind 不回退改动了"**(用户实测报告)—— 表面是一个 bug,查下去是两个,而且都只在真实使用中才暴露:
   - **绑定错了对象**:恢复目标是在**当前线程的日志里**按内容 id 反查的,而 redo 会往日志尾部追加新记录,于是同一次 rewind 在 redo 前后落到不同位置。根因是"回退到哪"这个问题被绑在了线程上,而线程会分叉——修正即决策 20。
   - **stat cache 的 racily-clean 陷阱**:agent 写文件与其后的 checkpoint 相隔毫秒级,若改动恰好不改变文件大小,`(size, mtime)` 指纹完全一致,快照于是记下了**旧内容的 hash**。目标与现状因此算出"零差异",恢复静默地什么都不做。
     - **二次修正(你的质疑:"指纹要包含 hash 吧")**:hash 不能进指纹——指纹存在的意义就是不读文件,hash 是被缓存的**值**而非**键**(git 同样这么切分:stat 数据做键,blob SHA 是省下来的计算)。但你怀疑得对,第一版修法不严密:它问的是"文件此刻是否新鲜",只覆盖写入后的头两秒;真正致命的是**第二次写入落在上一次读取的同一个 tick 里**,此后 mtime 和 size 永久不变,一分钟后的 checkpoint 看到的是一个完全"安定"的文件,照信不误。git 的做法是在**写入条目时一次性判定**并把可疑性记在条目自身上,之后永远不信它。现在同样:在自身 mtime 的 racy 窗口内被捕获的条目存一个全零指纹,`stat_matches` 直接拒绝匹配,直到某次 checkpoint 看到文件安定才记下真实指纹。
   - 教训:这两个都不是设计缺陷而是**绑定与时序**缺陷,只有让用户在真实工作区里连着 rewind/redo 才会浮现。
